# 需求分析与优先级

> 此文档原属于 `product/`，因其定位为 PM 方法论而非产品设计文档，移至归档。

VutronMusic 的需求可以归纳为以下四类来源：

| 来源 | 示例 | 权重考量 |
|------|------|---------|
| **用户反馈** | GitHub Issues、用户提的需求 | 高 frequency 优先 |
| **产品定位驱动** | 插件化重构、多源聚合 | 方向性的必须做 |
| **竞品对标** | 参考 YesPlayMusic 的 UI、Listen1 的多源 | 差异化权衡 |
| **技术演进** | Electron 升级、依赖安全更新 | 维护性需求，延期有成本 |

## 四象限优先级矩阵

将需求按 **用户影响**（Impact）和 **实现成本**（Effort）分为四类：

```
                    高 Impact
                        │
          ┌─────────────┼─────────────┐
          │             │              │
          │  Q1: 优先做  │  Q2: 规划做  │
          │  Quick Win   │  Major Bet  │
          │             │              │
          │  • 多源搜索  │  • 插件化    │
          │  • 本地歌词  │    重构      │
          │    匹配     │  • ADR 文档  │
 低 Effort ├─────────────┼─────────────┤ 高 Effort
          │             │              │
          │  Q3: 顺手做  │  Q4: 谨慎做  │
          │  Fill-in     │  Money Pit  │
          │             │              │
          │  • 国际化    │  • 全部      │
          │    补充     │    网易云    │
          │  • 快捷键    │    功能     │
          │    自定义    │    重写     │
          │             │              │
          └─────────────┼─────────────┘
                        │
                    低 Impact
```

**如何使用**：每个迭代先做 Q1，再评估 Q2 是否有资源，Q3 见缝插针，Q4 除非有强烈理由否则先放一放。

## 功能状态评估

| 功能 | 完成度 | 用户价值 | 优先级 | 说明 |
|------|--------|---------|--------|------|
| 多源搜索 | ✅ 基本完成 | ⭐⭐⭐⭐⭐ | P1 | 核心差异化功能 |
| 本地音乐扫描 | ✅ 基本完成 | ⭐⭐⭐⭐⭐ | P1 | 核心功能，需持续优化匹配准确率 |
| 插件系统 | ✅ 核心完成 | ⭐⭐⭐⭐⭐ | P1 | 架构基石，但 UI 层未完全解耦 |
| 桌面歌词 | ✅ 完成 | ⭐⭐⭐⭐ | P2 | 功能稳定，迭代空间小 |
| 音效系统 | ✅ 完成 | ⭐⭐⭐ | P2 | EQ/混响/变速，小众但高质量 |
| 网易云全面功能 | 🔄 部分迁移 | ⭐⭐⭐⭐ | P2 | 插件化迁移中 |
| 酷狗音乐 | ✅ 基本完成 | ⭐⭐⭐ | P2 | 覆盖率不如网易云 |
| 流媒体集成 | ✅ 完成 | ⭐⭐⭐⭐ | P1 | Navidrome/Emby/Jellyfin |
| 评论系统 | 🔄 部分实现 | ⭐⭐⭐ | P3 | 依赖插件能力，非核心 |
| 同步/跨设备 | ❌ 未开始 | ⭐⭐⭐ | P4 | 范围大，需明确方案 |
| 移动端 | ❌ 不考虑 | ⭐ | P99 | 超出产品边界 |

> P1 = 必须做好，P2 = 重要，P3 = 有价值，P4 = 未来考虑，P99 = 不会做。

## 功能需求模板

标准的产品需求描述格式：

```markdown
## 功能名称：[标题]

### 用户故事
作为 [用户类型]，我希望 [功能描述]，以便 [用户价值]。

### 验收标准
1. 当 [操作] 时，系统应该 [预期行为]
2. 当 [异常输入] 时，系统应该 [错误处理]

### 设计权衡
- 方案 A：[简述] — 优点/缺点
- 选定方案：[A/B]，理由：[为什么]

### 不做范围
- 明确不做什么（防止 scope creep）
```
