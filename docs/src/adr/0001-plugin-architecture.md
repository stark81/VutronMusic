# ADR-0001：插件架构选择

---

**状态**：已实施  
**日期**：v3.3.0 重构期间  
**决策者**：stark81（项目作者）

---

## Context

VutronMusic 需要支持多个音乐平台（网易云、酷狗、Navidrome 等）。在 v3.0 时代，每个平台的支持都意味着修改核心代码、增加新的 npm 依赖、在 IPC 中注册新的通道。这导致：

1. **耦合严重**：网易云的登录逻辑散落在主进程、preload、renderer 三个地方
2. **维护负担**：每个平台 API 变化都需要修改主程序
3. **僵化**：用户不能选择只用某些平台
4. **扩展困难**：第三方无法贡献新的平台支持

## 考虑的方案

### 方案 A：动态 require（Node.js 模块）

```
┌─ main ──────────────────────────────┐
│  const plugin = require('./plugin')  │
│  plugin.search(keyword)              │
└──────────────────────────────────────┘
```

- **优点**：简单，直接调用，性能好
- **缺点**：插件可以访问所有 Node.js API（无安全隔离）；一个插件的 crash 会拖垮整个主进程

### 方案 B：子进程（child_process）

```
┌─ main ─┐  IPC   ┌─ plugin process ─┐
│        │◄──────►│                  │
└────────┘        └──────────────────┘
```

- **优点**：进程级隔离，一个插件 crash 不影响其他
- **缺点**：进程启动开销大，通信序列化开销高，难以管理多个插件的生命周期

### 方案 C：Worker 线程（选定方案 🏆）

```
┌─ main ────┐  MessagePort  ┌─ Worker ─────┐
│           │◄─────────────►│              │
│  Plugin   │              │  plugin.js   │
│  Manager  │              │  (沙箱执行)   │
└───────────┘              └──────────────┘
```

- **优点**：线程级隔离，轻量，共享进程内存但独立执行上下文
- **优点**：安全沙箱（无 `fs` 模块、无 DOM、无 `require`）
- **优点**：主进程可以监控超时并强制销毁卡死的 Worker
- **缺点**：需要序列化/反序列化通信数据
- **缺点**：插件不能使用 npm 包（限制功能）

## Decision

选择 **方案 C：Worker 线程** 作为插件执行沙箱。

## Consequences

### 正面

- 插件开发简单：只需一个 `.js` 文件，不需要构建工具
- 安全隔离：域名白名单 + 受限的 API 工具
- 稳定性：一个插件的崩溃不影响主进程和其他插件
- 可测试性：每个插件可独立加载和测试
- 资源消耗低：相比进程，线程更轻量

### 负面

- 插件无法使用 npm 依赖 → 必须通过 `api.*` 工具函数提供常用能力
- 通信有序列化开销（实际测试 <10ms，用户无感知）
- 调试困难：Worker 中的错误信息不如主进程直观
- 插件需要理解异步调用模型

### 后续影响

- 62 个 API 方法的定义（PluginAPI）成为核心契约
- `api.*` 工具函数需要持续扩展以满足插件需求
- Worker Runner（`pluginRunner.ts`）需要维护请求-响应映射逻辑
